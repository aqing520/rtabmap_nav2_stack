# 点云导出与重定位优化记录

> 作者：Ziyang Wang  
> 日期：2026-06-01  
> 分支：dev_nanli_test

---

## 1. 背景

测试 HDL 全局重定位时发现两个问题：

- **重定位速度慢**：直接使用从 RTAB-Map 数据库导出的原始点云（最大 548 万点，84 MB），HDL 节点在全局搜索阶段耗时极长。
- **定位不准**：地下停车场等退化场景（重复列柱、大面积平整墙面）以及建图时混入的动态物体（车辆）导致 FPFH 特征区分度低，RANSAC 误匹配率高。工位场景重定位正常，但地下停车场持续失败，进一步分析发现 HDL 默认参数存在多处问题。

---

## 2. 本次改动

### 2.1 移除 PCD 导出时的 PLY 生成（`extract_pcd_from_db.py`）

删除 `write_ply_ascii` 函数及相关调用，导出脚本只生成 PCD（binary），不再生成 PLY。

PLY 文件体积约为 PCD 的 4 倍（ASCII 格式），对本项目无实际用途。

**使用方式不变：**
```bash
python3 scripts/extract_pcd_from_db.py [db路径] [输出目录]
```

---

### 2.2 自适应体素降采样（`global_localization_node.py`）

原来 `load_pcd_as_cloud2` 使用固定 `voxel_size=0.2m` 降采样。不同场景点云规模差异悬殊（10 万 ~ 548 万点），固定体素无法兼顾速度与精度。

**新机制：二分搜索体素大小，使降采样后点数收敛到目标值（默认 15 万 ±20%）。**

核心函数 `_adaptive_voxel_size`：

```
输入：原始点云、目标点数（默认 150,000）
过程：在 [voxel_min=0.05m, voxel_max=5.0m] 范围内二分，最多迭代 20 次
输出：降采样后点云、使用的体素大小、实际点数
```

三种分支：

| 情况 | 处理方式 |
|------|---------|
| 原始点数 ≤ 目标 | 不降采样，直接使用原始点云 |
| voxel_min 打底后点数仍低于目标（点云稀疏） | 不降采样，直接使用原始点云 |
| 原始点数 > 目标且可收敛 | 二分搜索，收敛到目标 ±20% |

**实测结果（加入高度过滤后，见 2.3 节）：**

| 场景 | 原始点数 | 高度过滤后 | 降采样后 | 体素大小 |
|------|---------|----------|---------|---------|
| 工位 | 242,355 | 152,203 | 152,203 | —（不降采样） |
| 地下停车场 | 5,484,079 | 1,753,135 | 131,879 | 0.205m |

传固定 `voxel_size` 参数时走老逻辑，向后兼容。

### 2.3 高度过滤（`global_localization_node.py`）

**问题**：点云中包含大量对定位无贡献甚至有害的点：
- `z < 0.1m`：地面反射，整个停车场/房间地面特征完全一样
- `z > 2.2m`：天花板、管道、灯具，大面积平整面，特征高度同质化
- 建图时停着的车（z 约 0.3~1.5m）被扫入地图，重定位时车已移走，造成假结构干扰匹配

**做法**：在自适应降采样之前先按高度裁剪，只保留 `z ∈ [0.1m, 2.2m]` 的点（柱子、墙角、桌椅等静态结构）。

完整处理流程：
```
加载 PCD → 高度过滤 [0.1m, 2.2m] → 自适应降采样（目标 15 万）→ 发给 HDL
```

停车场通过高度过滤去除了约 **68%** 的无效点（548万 → 175万），同时体素从 0.36m 缩小到 0.205m，特征细节保留更好。

---

### 2.4 新增 `--pcd` 参数（`start_with_global_localization.sh`）

原脚本只能通过 `--db` 指定 RTAB-Map 数据库，HDL 全局定位所用 PCD 固定取 `cloud_map/` 下按文件名排序最新的文件。多场景切换时无法指定特定点云。

新增 `--pcd` 参数，透传给 `global_localization_node.py`：

```bash
# 使用工位点云启动
bash scripts/start_with_global_localization.sh \
  --pcd cloud_map/rtabmap_20260528_142230_cloud.pcd

# 使用地下停车场点云启动
bash scripts/start_with_global_localization.sh \
  --pcd cloud_map/rtabmap_20260529_154954_cloud.pcd

# 不指定则自动取 cloud_map/ 下最新文件（默认行为不变）
bash scripts/start_with_global_localization.sh
```

参数说明：

| 参数 | 说明 | 默认值 |
|------|------|--------|
| `--db` | RTAB-Map 数据库，用于持续定位跟踪 | `/data/maps/site_a/rtabmap.db` |
| `--pcd` | HDL 全局定位所用点云地图 | `cloud_map/` 下最新 PCD |
| `--engine` | 匹配算法 `FPFH_RANSAC` / `BBS` | `FPFH_RANSAC` |

### 2.5 HDL 参数调优（`ransac_config.yaml` / `general_config.yaml`）

**问题根因分析**：

1. **HDL 内部二次降采样**：`globalmap_downsample_resolution: 0.5m`，无论 Python 端传入多少点，HDL 都会再降到 0.5m 体素。停车场大空间中 0.5m 体素后走廊结构特征几乎全部丢失。

2. **对应距离过松**：`max_correspondence_distance: 1.0m`，在 0.5m 体素的点云上，1m 容差意味着任意两个相邻体素格的点都能算内点，大量假匹配把内点率撑高但位姿错误。

3. **未约束地面机器人姿态**：`roll/pitch ±3.15 rad`（即 ±180°），地面机器人 roll/pitch 几乎为零，RANSAC 在全球面搜索浪费大量迭代预算，真实解概率被稀释。

4. **内点比例门槛过低**：`inlier_fraction: 0.25`，25% 配合松散的对应距离，允许大量错误匹配通过。

**参数变更：**

| 文件 | 参数 | 原值 | 新值 | 原因 |
|------|------|------|------|------|
| `ransac_config.yaml` | `max_correspondence_distance` | 1.0m | **0.5m** | 对齐 0.3m 体素，减少假内点 |
| `ransac_config.yaml` | `roll_min/max` | ±3.15 | **±0.1** | 地面机器人约束 |
| `ransac_config.yaml` | `pitch_min/max` | ±3.15 | **±0.1** | 地面机器人约束 |
| `ransac_config.yaml` | `inlier_fraction` | 0.25 | **0.35** | 提高匹配质量门槛 |
| `general_config.yaml` | `globalmap_downsample_resolution` | 0.5m | **0.3m** | 保留更多结构细节 |
| `general_config.yaml` | `query_downsample_resolution` | 0.5m | **0.3m** | 同上 |

修改后同步到 `install/` 目录（HDL 节点运行时读取路径）。
