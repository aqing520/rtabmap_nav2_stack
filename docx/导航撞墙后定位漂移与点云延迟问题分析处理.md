# 导航撞墙后定位漂移与点云延迟问题分析处理

**日期**: 2026-07-13  
**适用项目**: `rtabmap_nav2_stack`  
**涉及链路**: Livox MID360 → FAST-LIO → RTAB-Map → Nav2 → collision_monitor

---

## 1. 问题现象

导航过程中，机器人发生撞墙后出现定位漂移。现场同时观察到局部防撞效果变差，机器人对近距离墙体/障碍反应滞后。

实测主要现象如下：

1. **撞墙后定位姿态异常**
   - `/Odometry` 中 `base_footprint` 出现明显 3D 姿态偏移。
   - 现场曾观察到近似值：
     - `roll ≈ -35°`
     - `pitch ≈ -11°`
     - `z ≈ -1.4 m`
   - 对于平地移动机器人，`base_footprint` 正常应接近：
     - `roll = 0`
     - `pitch = 0`
     - `z = 0`

2. **点云和里程计存在 1 秒以上延迟**
   - `/cloud_registered_body` 和 `/Odometry` 存在约 `1.3 ~ 2.1 s` 的时间滞后。
   - RTAB-Map 日志中可见：

   ```text
   delay=1.4~2.3s
   ```

3. **collision_monitor 丢弃点云**
   - 日志中持续出现：

   ```text
   [pointcloud]: Latest source and current collision monitor node timestamps differ on 1.3~1.9 seconds. Ignoring the source.
   ```

   这表示防撞模块认为点云过旧，直接忽略该点云源。

4. **系统 CPU 负载较高**
   - 同时运行 FAST-LIO、Livox driver、Orbbec 相机、RTAB-Map、rtabmap_viz、RViz、Nav2 controller、costmap 和 collision_monitor。
   - 多个节点 CPU 占用较高，Nav2 controller 出现控制周期 missed。

---

## 2. 当前导航链路

当前系统大致链路如下：

```text
Livox MID360
  ├─ /livox/lidar
  └─ /livox/imu
        ↓
FAST-LIO /laser_mapping
  ├─ /Odometry               odom -> base_footprint
  └─ /cloud_registered_body  base_footprint 下的去畸变点云
        ↓
RTAB-Map
  ├─ /map
  └─ map -> odom
        ↓
Nav2
  ├─ global_costmap
  ├─ local_costmap
  ├─ controller_server
  └─ collision_monitor
        ↓
/cmd_vel
```

其中：

- FAST-LIO 发布 `odom -> base_footprint` 和 `/Odometry`。
- RTAB-Map 发布 `map -> odom`。
- Nav2 使用 `/map`、`/Odometry` 和 `/cloud_registered_body` 做规划、避障和防撞。

---

## 3. 根因分析

### 3.1 撞墙导致 FAST-LIO 状态发散

FAST-LIO 依赖激光和 IMU 做紧耦合里程计。撞墙瞬间会带来：

- 机体强冲击和高频振动；
- IMU 瞬时加速度异常；
- 雷达近距离墙面点云退化；
- 机器人真实运动与模型预测不一致；
- 点云匹配残差突然变差。

这些因素会导致 FAST-LIO 的状态估计被带偏。一旦 FAST-LIO 的 `odom -> base_footprint` 漂移，RTAB-Map 和 Nav2 后续都会基于错误位姿工作。

特别需要注意：当前 FAST-LIO 配置中存在：

```yaml
mapping:
  extrinsic_est_en: true
```

开启在线外参估计时，撞击或剧烈振动可能把 IMU-LiDAR 外参也带偏，进一步放大定位漂移。

### 3.2 3D 姿态直接进入 Nav2

FAST-LIO 输出的是 3D 位姿，包含 `x/y/z/roll/pitch/yaw`。但 Nav2 的 2D 导航通常只希望使用：

```text
x, y, yaw
```

如果 `base_footprint` 带有明显 `roll/pitch/z`，会影响：

- local costmap 坐标变换；
- collision_monitor 点云投影；
- RTAB-Map 输入位姿；
- RViz 中机器人模型与地图对齐；
- 全局/局部路径跟踪效果。

因此撞墙后 FAST-LIO 一旦出现 3D 姿态发散，Nav2 会出现定位偏移、障碍位置偏移、防撞不稳定等连锁问题。

### 3.3 点云延迟导致防撞失效

`collision_monitor` 使用 `/cloud_registered_body` 做近距离防撞。现场日志显示点云延迟超过 `source_timeout`，因此被忽略。

现象：

```text
Latest source and current collision monitor node timestamps differ on 1.3~1.9 seconds. Ignoring the source.
```

这说明：

- 防撞模块不是没有收到点云；
- 而是收到的点云时间戳太旧；
- 因此 collision_monitor 不使用该点云。

如果机器人速度为 `0.6 m/s`，`1.5 s` 的延迟意味着机器人已经多走：

```text
0.6 m/s × 1.5 s = 0.9 m
```

而当前防撞 StopZone 只有几十厘米时，机器人实际接触障碍前已经来不及停下。

### 3.4 系统负载过高导致消息排队

点云延迟主要来自处理链路拥塞，而不是单纯网络延迟。

高负载来源包括：

- Livox driver 接收和发布高频雷达数据；
- FAST-LIO 做点云去畸变、匹配和地图维护；
- RTAB-Map 做图优化、定位和地图发布；
- Orbbec RGBD 相机持续输出图像；
- `rgbd_sync` 做同步；
- `rtabmap_viz` 和 RViz 同时订阅大点云、地图、路径；
- local/global costmap 同时订阅 `/cloud_registered_body`；
- collision_monitor 也订阅同一份点云。

`/cloud_registered_body` 的订阅者较多时，DDS 分发和序列化开销会上升，低算力平台上容易出现消息积压。

## 4. 排查方法

### 4.1 查看节点是否正常

```bash
source /opt/ros/humble/setup.bash
source ~/xz/rtabmap_nav2_stack/install/setup.bash
export ROS2CLI_ENABLE_DAEMON=0
ros2 node list
```

重点确认以下节点：

```text
/laser_mapping
/rtabmap
/controller_server
/local_costmap/local_costmap
/global_costmap/global_costmap
/collision_monitor
/livox_lidar_publisher
```

### 4.2 查看话题频率

```bash
ros2 topic hz /livox/lidar
ros2 topic hz /livox/imu
ros2 topic hz /Odometry
ros2 topic hz /cloud_registered_body
```

参考判断：

| 话题 | 期望 | 异常表现 |
|------|------|----------|
| `/livox/imu` | 高频稳定 | 丢包、长时间无输出 |
| `/livox/lidar` | 接近配置频率，如 10Hz | 明显低于配置频率 |
| `/Odometry` | 连续稳定 | 频率低、抖动大、延迟大 |
| `/cloud_registered_body` | 连续稳定 | 频率低、延迟大 |

### 4.3 查看点云时间戳延迟

可以用以下思路检查消息时间戳与当前时间差：

```bash
ros2 topic echo /cloud_registered_body --field header --once
ros2 topic echo /Odometry --field header --once
```

如果当前系统时间与消息 header stamp 相差超过 `0.5s`，需要重点排查。超过 `1s` 时，防撞和局部避障风险较高。

### 4.4 查看防撞日志

```bash
ros2 topic echo /rosout
```

重点搜索：

```text
collision_monitor
Ignoring the source
Latest source and current collision monitor node timestamps differ
```

若持续出现，说明 collision_monitor 正在丢弃点云。

### 4.5 查看 FAST-LIO 输出姿态

```bash
ros2 topic echo /Odometry --once
```

重点检查：

```text
pose.pose.position.z
pose.pose.orientation
```

平地机器人如果出现明显 `z` 偏移或大 `roll/pitch`，说明 FAST-LIO 状态已经不适合作为 Nav2 2D 导航输入。

## 5. 处理方案

### 5.1 现场临时处理

发生撞墙并出现定位漂移后，应立即执行：

1. 停止导航任务；
2. 停止底盘运动；
3. 重启 FAST-LIO、RTAB-Map 或整个 bringup；
4. 必要时重新给初始位姿或重新全局重定位；
5. 确认 `/Odometry` 中 `z/roll/pitch` 恢复正常后再继续导航。

不要在 FAST-LIO 已经发散的状态下继续导航，否则 RTAB-Map 和 Nav2 会继续基于错误位姿运行。

### 5.2 关闭 FAST-LIO 在线外参估计

建议修改：

```yaml
# src/FAST_LIO_ROS2/config/mid360.yaml
mapping:
  extrinsic_est_en: false
```

说明：

- 外参应在线下标定后固定；
- 导航运行时不建议继续在线估计外参；
- 撞击、振动、退化场景可能把在线外参估计带偏。

### 5.3 给 Nav2 使用 2D 化后的里程计/TF

建议新增或修改 FAST-LIO 输出，使 Nav2 消费的 `odom -> base_footprint` 只包含：

```text
x, y, yaw
```

并强制：

```text
z = 0
roll = 0
pitch = 0
```

可选实现方式：

#### 方式 A：在 FAST-LIO 发布 odom TF 时直接 2D 化

优点：链路短，Nav2 直接使用稳定的 2D TF。  
缺点：会丢失 FAST-LIO 的完整 3D 姿态，不适合同时需要 3D 建图显示的场景。

#### 方式 B：保留 FAST-LIO 3D odom，新增 2D odom bridge

建议链路：

```text
FAST-LIO 原始输出:
  /Odometry_raw
  odom_raw -> base_link_3d

2D bridge 输出:
  /Odometry
  odom -> base_footprint
```

优点：

- FAST-LIO 3D 信息仍保留；
- Nav2 只使用稳定 2D 信息；
- 更符合 2D 导航约定。

### 5.4 降低点云处理负载

可尝试调整 FAST-LIO 参数：

```yaml
# src/FAST_LIO_ROS2/config/mid360.yaml
point_filter_num: 3
filter_size_surf: 0.25
filter_size_map: 0.25
```

含义：

- `point_filter_num` 增大：减少参与处理的点数；
- `filter_size_surf` 增大：降低局部特征点密度；
- `filter_size_map` 增大：降低地图维护压力。

调整后需要重新测试定位稳定性，避免过度降采样导致匹配质量下降。

### 5.5 导航时关闭不必要可视化

正式导航时建议关闭：

- RViz；
- rtabmap_viz；
- 不必要的点云显示；
- 不必要的 RGBD 输入。

启动建议：

```bash
ros2 launch robot_bringup bringup_orbbec.launch.py \
  mode:=navigation \
  sensor_profile:=lidar_only \
  start_livox:=true \
  start_camera:=false \
  enable_rviz:=false \
  use_sim_time:=false \
  database_path:=/home/wheeltec/xz/rtabmap_nav2_stack/rtabmap_orbbec.db
```

如果必须使用 RGBD，则建议关闭 `rtabmap_viz`，并确认 CPU 负载和点云延迟满足要求。

### 5.6 降低导航速度并扩大防撞区

在点云延迟未彻底解决前，应先降低速度。

建议调试阶段：

```yaml
max_vel_x: 0.20 ~ 0.30
max_vel_theta: 0.50 ~ 0.80
```

collision_monitor 建议：

```yaml
StopZone.points: [0.80, 0.35, 0.80, -0.35, -0.15, -0.35, -0.15, 0.35]
SlowZone.points: [1.30, 0.45, 1.30, -0.45, -0.25, -0.45, -0.25, 0.45]
```

注意：扩大防撞区只是降低撞击风险，不能替代点云延迟治理。

### 5.7 不建议简单调大 source_timeout

不建议直接把 collision_monitor 的：

```yaml
source_timeout: 1.0
```

简单调大到 `2.0s` 或更高来消除报警。

原因：

- 报警会少；
- 但 collision_monitor 使用的是旧点云；
- 机器人仍可能按过期障碍信息运动；
- 实际防撞效果可能更差。

正确方向是减少点云延迟，而不是容忍旧点云。

## 6. 推荐修改优先级

### 优先级 P0：立即执行

1. 撞墙后立即停止任务并重启定位链路；
2. 导航时关闭 RViz 和 rtabmap_viz；
3. 降低最大线速度到 `0.2 ~ 0.3 m/s`；
4. 扩大 StopZone 和 SlowZone。

### 优先级 P1：参数修复

1. FAST-LIO 关闭在线外参估计：

   ```yaml
   extrinsic_est_en: false
   ```

2. 适当降低 FAST-LIO 点云处理负载：

   ```yaml
   point_filter_num: 3
   filter_size_surf: 0.25
   filter_size_map: 0.25
   ```

3. 不需要 RGBD 定位时，切换到 `lidar_only`。

### 优先级 P2：结构优化

1. 增加 2D odom bridge，给 Nav2 独立发布 2D 化 `/Odometry` 和 `odom -> base_footprint`；
2. 保留 FAST-LIO 原始 3D 输出用于调试或建图；
3. 增加定位健康监控节点，监控：
   - `/Odometry` 延迟；
   - `/cloud_registered_body` 延迟；
   - `z/roll/pitch` 是否超限；
   - RTAB-Map `delay` 和定位质量；
   - collision_monitor 是否持续丢弃点云。

---

## 7. 验收标准

处理完成后，建议按以下标准验收：

| 项目 | 目标 |
|------|------|
| `/cloud_registered_body` 延迟 | 小于 `0.3 ~ 0.5s` |
| `/Odometry` 延迟 | 小于 `0.2 ~ 0.5s` |
| collision_monitor 日志 | 不再持续出现 `Ignoring the source` |
| 平地静止时 z | 接近 `0` |
| 平地静止时 roll/pitch | 接近 `0°` |
| controller_server | 不持续出现 missed rate |
| 低速靠墙测试 | 能在 StopZone 前停止 |
| 撞击/急停后 | 定位不应出现大幅跳变 |

---

## 8. 总结

本次问题不是单一的 Nav2 参数问题，而是以下因素叠加导致：

1. 撞墙冲击导致 FAST-LIO 里程计状态发散；
2. FAST-LIO 的 3D 姿态直接进入 2D 导航链路；
3. 点云处理链路延迟达到 `1s` 以上；
4. collision_monitor 因点云过期而丢弃防撞数据；
5. RViz、rtabmap_viz、RGBD 和多点云订阅导致系统负载过高。

推荐治理方向：

```text
先降速和减负载，恢复防撞有效性；
再固定 FAST-LIO 外参，避免撞击后外参漂移；
最后将 Nav2 输入改为 2D 化 odom/TF，提高导航鲁棒性。
```
