# 导航长期运行出现 25.6 秒超强延迟的实测对比报告

> 历史记录：本文保留旧版本性能数据。在线地图编辑和禁行区编辑功能已于 2026-07-30 从当前工程中删除，文中的相关启动参数仅用于还原历史问题。

**报告日期**：2026-07-27  
**项目目录**：`/home/wheeltec/xz/rtabmap_nav2_stack`  
**对比目标**：用默认启动方式的长期稳定数据，对比此前“编辑地图 + 地图编辑器 + 禁行区”运行约 30 分钟后出现的 `25.6 s` 极端延迟，证明当前导航系统确实存在长期运行后发生超强延迟的风险。

---

## 1. 最终结论

### 1.1 已经可以明确证明的问题

当前系统**确实出现过长期运行后的超强延迟**，不是视觉错觉，也不是 RViz 单独卡顿。

此前编辑地图组合运行约 30 分钟后实测：

```text
/Odometry                  中位延迟 25.588 s
/cloud_registered_body     中位延迟 25.589 s
/livox/imu                 中位延迟  0.003 s
```

同时：

```text
/Odometry                  仅 1.84 Hz
/cloud_registered_body     仅 1.92 Hz
load average               约 13.09
CPU idle                   约 16.7%
TF extrapolation errors    211 次
global costmap 丢包         131 次
```

这组数据能够直接证明：

1. FAST-LIO 点云和里程计正在发布约 `25.6 s` 前的历史状态；
2. 点云和里程计同时变慢，延迟位置在 FAST-LIO 主处理链路，而不是 RViz 显示端；
3. IMU 仍接近实时，排除了整机时间统一偏移 `25 s` 的解释；
4. FAST-LIO 输出从正常约 `10 Hz` 下降到约 `1.9 Hz`，已经无法跟上雷达输入；
5. TF、costmap、Collision Monitor 和导航异常都是旧数据继续向下游传播的结果。

因此，本报告的核心结论不是“可能有一点延迟”，而是：

> **当前软件组合已经实测发生过约 25.6 秒的超强延迟，且该延迟足以使定位、规划、控制和防撞全部失去实时意义。**

### 1.2 与默认长时间测试的直接差距

默认脚本连续测试 10 分钟后，成熟阶段的典型延迟为：

```text
/Odometry                  约 1.37 s
/cloud_registered_body     约 1.41 s
```

与 `25.6 s` 极端现场相比：

| 对比项 | 默认 10 分钟稳定阶段 | 长期极端现场 | 放大倍数 |
|---|---:|---:|---:|
| 里程计中位延迟 | 1.367 s | 25.588 s | **18.72 倍** |
| 点云中位延迟 | 1.414 s | 25.589 s | **18.10 倍** |
| 里程计频率 | 约 10 Hz | 1.84 Hz | **下降约 81.6%** |
| 点云频率 | 约 10 Hz | 1.92 Hz | **下降约 80.8%** |

这不是普通的几十毫秒抖动，而是从“约 1.4 秒偏慢”恶化成“约 25.6 秒历史数据回放”。

## 4. 之前约 30 分钟后的 25.6 秒超强延迟

### 4.1 现场测量结果

编辑地图组合从约 `16:24` 开始运行，在约 `16:55` 进行测量，即已经持续运行约 30 分钟。

| 话题 | 消息频率 | 中位延迟 | 最大延迟 |
|---|---:|---:|---:|
| `/Odometry` | 1.84 Hz | **25.588 s** | 25.692 s |
| `/cloud_registered_body` | 1.92 Hz | **25.589 s** | 25.741 s |
| `/livox/imu` | 174.90 Hz | **0.003 s** | 0.059 s |

### 4.2 这是“队列积压”，不是单纯掉帧

如果系统只是算力不足并立即丢弃旧帧，可能会出现：

```text
输出频率下降，但输出仍然接近当前时刻
```

实际看到的是：

```text
输出频率下降到约 1.9 Hz
+
输出内容落后当前时刻约 25.6 s
```

这证明处理链路在继续消费历史消息，旧消息没有及时丢弃，队列长度不断增长。

可以将过程表示为：

```text
LiDAR 按约 10 Hz 输入
        ↓
FAST-LIO 实际只能按约 1.9 Hz 输出
        ↓
每秒新增的输入多于能够处理的输入
        ↓
待处理队列越来越长
        ↓
点云和里程计从 1～2 秒旧，发展到 5 秒、10 秒、25.6 秒旧
```

### 4.3 IMU 数据证明不是系统时间错误

极端阶段 IMU 为：

```text
174.90 Hz
中位延迟 0.003 s
```

而 FAST-LIO 输出为：

```text
约 1.9 Hz
中位延迟约 25.6 s
```

如果是电脑系统时间整体错误，IMU 也应出现相近的 `25 s` 偏差。但 IMU 仍接近实时，因此可以排除：

- 整机时间突然慢了 25 秒；
- 所有 ROS 节点统一时间错位；
- 仅仅是 RViz 显示缓存。

延迟是在 LiDAR/FAST-LIO 处理链路及其 DDS 分发过程中累积出来的。

### 4.4 同期系统过载证据

极端延迟阶段：

```text
load average ≈ 13.09
CPU idle ≈ 16.7%
TF extrapolation errors = 211
global costmap Message Filter drops = 131
```

说明系统已经没有足够实时余量：

- FAST-LIO 来不及处理输入；
- TF 中使用的是旧位姿；
- global costmap 等不到对应时间的 TF；
- Message Filter 队列被塞满；
- Collision Monitor 会忽略过旧点云；
- Nav2 根据几十秒前的位置和障碍物继续计算。

## 6. 25.6 秒延迟对导航意味着什么

### 6.1 定位已经失去实时意义

当 `/Odometry` 落后 `25.6 s` 时，Nav2 看到的是机器人约 25 秒前的位置。

例如机器人速度如果为 `0.6 m/s`，理论上 25.6 秒可以移动：

```text
0.6 × 25.6 = 15.36 m
```

即使实际机器人受环境限制没有移动这么远，该量级也说明控制闭环已经完全失效。

### 6.2 点云障碍位置严重过期

`/cloud_registered_body` 落后 `25.6 s`，意味着：

- 当前出现的障碍物还没有进入 costmap；
- 25 秒前已经离开的障碍可能仍被当成当前障碍；
- local/global costmap 的快速计算没有意义，因为输入本身已经过期；
- Collision Monitor 会因为点云超过 `source_timeout` 而直接忽略安全源。

### 6.3 控制器会形成迟滞振荡

控制器根据旧位置输出转向，机器人真正转动后，新的里程计要 25 秒后才进入控制器。由此会出现：

```text
旧误差触发转向
  ↓
机器人已经转过，但控制器仍看见旧姿态
  ↓
继续过量转向
  ↓
延迟状态到达后再向相反方向修正
  ↓
S 形、左右振荡、原地旋转、撞墙风险
```

因此定位漂移、导航振荡和点云延迟不是三个互不相关的问题，而可能是同一个延迟闭环的不同表现。

## 8. 为什么启用地图编辑组合后更容易触发

### 8.1 两个 `/map` 发布者

实测发布关系：

```text
默认方式：
  /map 只有 /rtabmap 一个发布者

编辑地图组合：
  /map 同时由 /map_server 和 /map_paint_editor 发布
```

两个 transient-local 地图发布者会导致：

- 地图来源不唯一；
- 全图重复分发；
- global costmap static layer 更新；
- RViz 地图重绘；
- 代价地图更新峰值；
- DDS 大消息拷贝增加。

### 8.2 地图编辑器会清除 costmap 并重发目标

现场参数：

```yaml
clear_global_costmap_on_publish: true
reissue_goal_on_publish: true
costmap_clear_min_interval_sec: 0.75
goal_reissue_min_interval_sec: 1.0
```

此前日志记录：

```text
global costmap clears = 14
local costmap clears  = 10
controller goals      = 11
empty path errors     = 11
```

每次清图和重发目标都会触发 costmap、规划器、行为树和控制器重新工作，形成瞬时高负载。

### 8.3 禁行区多边形不是主要直接原因

现场配置中：

```yaml
forbidden_areas: []
```

说明当时没有大量禁行多边形参与计算。`forbidden_area_visualizer` 平均 CPU 也只有约 `0.53%`。

因此，不能简单归因于“禁行区多边形计算太慢”。主要问题是整个编辑地图启动组合增加的节点、地图发布、GUI、costmap 更新和系统竞争。

### 8.4 编辑地图还存在 unknown 被转成 free 的错误

PGM 文件实际像素：

| 灰度值 | 原始语义 | 数量 |
|---:|---|---:|
| 0 | occupied | 1,937 |
| 205 | unknown | 132,792 |
| 254 | free | 90,865 |

但编辑地图发布后的 `/map` 曾统计为：

```text
unknown  = 0
free     = 223657
occupied = 1937
```

即全部 `132792` 个未知栅格被当成自由区域。

这会让规划器进入原本未探索的室外区域，并可能产生长时间原地旋转或错误路径。室外空旷、纯旋转又会降低 FAST-LIO 可观测性，使定位发散和延迟问题互相放大。

## 9. FAST-LIO 当前参数对负载的影响

当前 MID360 主要参数：

```yaml
point_filter_num: 2
filter_size_surf: 0.20
filter_size_map: 0.20
cube_side_length: 1000.0
preprocess.scan_rate: 10
common.time_offset_lidar_to_imu: 0.0
mapping.extrinsic_est_en: true
```

`0.20 m` 体素和 `point_filter_num: 2` 保留的点较多，会同时增加：

- FAST-LIO 最近邻搜索和地图更新；
- 点云发布数据量；
- DDS 序列化和订阅反序列化；
- RViz、STVL、Collision Monitor 的处理量。

建议按阶梯测试：

```yaml
# 第一档
point_filter_num: 3
filter_size_surf: 0.25
filter_size_map: 0.25

# 如果长期仍不能维持实时，再测试第二档
point_filter_num: 4
filter_size_surf: 0.30
filter_size_map: 0.30
```

导航阶段如果 LiDAR-IMU 外参已经标定并固定，应测试：

```yaml
mapping.extrinsic_est_en: false
```

但必须注意：调滤波参数只能降低计算量，不能代替地图语义修复、单一 `/map` 发布者和队列丢旧策略。

## 10. 必须采取的修改

### P0：延迟超限立即停止导航

增加运行时监控：

```text
/cloud_registered_body
/Odometry
/livox/imu
/livox/lidar
```

建议安全策略：

```text
延迟 > 0.5 s：警告
延迟 > 1.0 s：限制速度
延迟 > 2.0 s：取消目标并停车
```

25.6 秒状态下禁止继续输出运动指令。

### P0：正式导航关闭在线地图编辑器

推荐使用方式：

```text
离线编辑：
  启动 map_paint_editor
  编辑并保存 PGM/YAML

正式导航：
  use_edited_map:=true
  start_map_paint_editor:=false
  只保留 map_server 发布 /map
```

### P0：修复 unknown → free

修改：

```text
src/map_paint_editor_plugin/scripts/map_editor/storage.py
```

确保灰度 `205` 加载后保持 OccupancyGrid 的 `-1`，并增加自动校验：

```text
编辑地图发布后 unknown 数量应接近 132792，不能等于 0
```

### P1：关闭自动清图和目标重发

```yaml
clear_global_costmap_on_publish: false
reissue_goal_on_publish: false
```

地图确认保存后，只允许人工触发一次清图和重新规划。

### P1：降低大消息负载

- 不再使用 `ros2 bag record -a`；
- 降低 Orbbec 图像分辨率、帧率或使用压缩；
- 正式导航关闭不必要的 RViz 点云显示；
- 减少 FAST-LIO 派生点云发布；
- 使用点云滤波阶梯测试；
- 诊断时不要同时开启多个 `ros2 topic echo/hz` 点云订阅。

### P1：FAST-LIO 必须丢旧保新

如果处理不过来，应优先丢弃旧 LiDAR 帧并追到最新时刻，而不是扩大队列。

```text
错误方向：扩大 queue depth，让历史数据继续排队
正确方向：限制队列，只保留最新数据，并降低单帧计算量
```

---

## 11. 修改后的长期验收要求

短时启动正常不能作为验收结果。每种启动方式都必须连续运行至少 `30 min`，并包含安全的真实导航运动。

### 11.1 需要持续记录

```text
每秒记录：
  系统 CPU busy
  load average
  MemAvailable
  各节点 CPU、RSS

持续记录：
  /livox/lidar 数据年龄
  /livox/imu 数据年龄
  /cloud_registered_body 数据年龄
  /Odometry 数据年龄
  TF extrapolation 错误数
  Message Filter drops
  Collision Monitor stale source 次数
  costmap clear 次数
  goal 重发次数
```

### 11.2 验收线

| 指标 | 要求 |
|---|---:|
| FAST-LIO 点云长期频率 | ≥ 9 Hz |
| FAST-LIO 里程计长期频率 | ≥ 9 Hz |
| 点云动态延迟 | 最好 < 0.3 s，必须 < 1.0 s |
| 里程计动态延迟 | 最好 < 0.3 s，必须 < 1.0 s |
| 30 分钟末相对 5 分钟延迟增长 | < 0.2 s |
| Collision Monitor 过期点云 | 0 次 |
| 连续 TF extrapolation 错误 | 0 次 |
| 正式导航 `/map` 发布者 | 1 个 |

一旦延迟随时间持续上升，即使暂时还只有 `2～3 s`，也应判定为不合格，因为故障数据已经证明它可能继续增长到 `25.6 s`。

## 12. 最终证明结论

通过三组数据可以形成完整证据链：

```text
默认长期基线：
  点云/里程计约 1.4 s，10 分钟内基本稳定

故障 rosbag：
  点云约 4.7 s，里程计约 5.4 s，最大接近 10 s

长期极端现场：
  点云和里程计同时达到约 25.6 s，频率下降到约 1.9 Hz
```

同时极端现场 IMU 仍为约 `0.003 s`，证明不是全系统时间偏移；CPU、load、TF 和 costmap 丢包记录又证明当时系统处于处理能力不足和消息队列崩溃状态。

因此可以明确写出：

> **当前导航系统在启用编辑地图、在线地图编辑器和禁行区组合，并叠加 RTAB-Map、相机、RViz、Nav2 等负载长期运行后，已经实测出现过约 25.6 秒的超强点云与里程计延迟。该问题会导致导航使用历史定位和历史障碍物数据，属于严重的实时性与安全问题。**

需要强调的是，这份证据证明的是：

```text
该超强延迟已经真实发生，当前系统具备再次出现的条件和风险。
```

它不表示每次启动都必然在相同分钟数达到完全相同的 `25.6 s`。触发时间会受机器人运动、室外退化、相机/RViz、录包、诊断订阅、地图发布和 CPU 调度影响，但不能再用刚启动时的短时正常结果否定这个长期故障。
