# 跨楼层导航总体技术方案报告

## 摘要

本报告面向 `xz/rtabmap_nav2_stack` 项目，讨论移动机器人跨楼层导航的总体设计思路。项目当前采用 Livox MID360、FAST-LIO、RTAB-Map 和 Nav2 构成导航链路，已经具备单楼层建图、定位、全局重定位、路径规划和多航点执行能力。但跨楼层任务不仅是一个更远的导航目标，而是地图、定位参考系、运动方式和任务控制模式同时发生变化的复合任务。

因此，跨楼层导航不宜被理解为“在一张三维地图上从起点规划到终点”，而应被建模为“楼层内二维导航与楼层间特殊通行行为的组合”。系统在楼层内部继续使用成熟的 Nav2 导航，在楼层连接区域切换为与连接设施相匹配的专用控制方式，并由上层任务管理器完成地图切换、状态管理和重新定位。

报告重点阐述系统分层、地图组织、拓扑规划、跨层连接器、状态机、重新定位、安全约束和实施步骤，不限定具体跨层方式，可同时适用于电梯、楼梯、坡道、升降平台和人工转运等场景。

## 1. 项目现状与问题定义

### 1.1 当前导航系统

项目当前主要数据链路为：

```text
Livox MID360
    ↓
FAST-LIO：连续里程计，发布 odom → base_footprint
    ↓
RTAB-Map：建图、回环和定位，发布 map → odom 与二维地图
    ↓
Nav2：全局规划、局部规划、运动控制和动态避障
```

该系统适合机器人在一个连续平面内运动。Nav2所使用的目标点和路径都位于当前 `map` 坐标系中，其规划基础仍是二维占据栅格。即使RTAB-Map保存了三维点云信息，Nav2也不会自然理解“同一XY位置但位于不同高度”的两个楼层。

### 1.2 跨楼层导航的本质

跨楼层任务包含三个性质不同的阶段：

1. 当前楼层内的常规导航；
2. 通过楼层连接设施完成空间转换；
3. 在目标楼层建立新的地图定位关系并继续导航。

其中第二阶段可能是乘坐电梯、爬楼梯、通过坡道、使用升降平台或由人工搬运。不同方式的运动能力、传感器表现和安全条件差异很大，不能全部交给同一个二维路径规划器处理。

因此，系统设计的关键不在于修改Nav2使其直接规划三维路线，而在于建立一个高于Nav2的任务层，将完整任务拆分成多个可验证、可恢复的阶段。

## 2. 总体设计思想

### 2.1 分层导航

推荐采用三层结构：

```text
任务层：理解目标楼层，规划跨楼层任务，管理状态与异常

拓扑层：选择楼层连接器，决定经过哪些楼层和连接区域

执行层：Nav2楼层内导航 + 专用跨层控制器 + 地图切换与重定位
```

任务层接收“去三楼某房间”这样的完整目标。拓扑层把建筑抽象成由楼层和连接设施组成的图。执行层再把拓扑路径逐段转换为Nav2目标或专用运动指令。

这种结构保留了现有Nav2系统的稳定性，也使跨层设施可以独立替换。未来增加新楼梯、新坡道或第二部电梯时，不需要重写楼层内导航模块。

### 2.2 任务分解

一个典型跨楼层任务可分解为：

```text
导航到当前楼层连接器入口
→ 对准并确认连接器可用
→ 进入跨层模式
→ 完成楼层间移动
→ 确认目标楼层或目标平台
→ 加载目标楼层地图
→ 在目标楼层重新定位
→ 退出连接区域
→ 导航到最终目标
```

每个阶段都应有明确的进入条件、成功条件、超时条件和失败处理。只有前一阶段被可靠确认后，系统才能进入下一阶段。

## 3. 地图组织方案

### 3.1 每层独立地图

建议为每个楼层保存独立的RTAB-Map数据库和用于全局重定位的点云地图：

```text
/data/maps/building_a/
├── floor_1/
│   ├── rtabmap.db
│   └── global_map.pcd
├── floor_2/
│   ├── rtabmap.db
│   └── global_map.pcd
└── floor_3/
    ├── rtabmap.db
    └── global_map.pcd
```

每层地图拥有自己的二维坐标系。不同楼层中的相同坐标不表示同一个物理位置，楼层编号是导航目标不可缺少的一部分。

独立地图的主要优点是避免二维投影重叠，降低单张地图规模，并允许每层单独更新和验证。其代价是跨层后必须显式切换地图并重新定位，但这正是跨楼层任务本来就需要完成的步骤。

### 3.2 连接区域标定

每个连接器在相关楼层地图中应保存若干语义位姿：

- `approach_pose`：机器人正常导航的等待位置；
- `alignment_pose`：切换专用控制前的对准位置；
- `entry_pose`：进入连接区域的位置；
- `exit_pose`：目标楼层离开连接区域的位置；
- `relocalization_pose`：适合采集环境特征并重新定位的位置。

这些位姿属于对应楼层地图，不能简单地把一楼入口坐标复制到二楼。建立地图后，需要分别在每层完成标定和实车验证。

## 4. 建筑拓扑模型

### 4.1 楼层与连接器

建筑可抽象为一张拓扑图：

```text
一楼 ── 楼梯A ── 二楼 ── 楼梯A ── 三楼
 │                    │
 └── 坡道B ──────────┘
```

图中的节点可以表示楼层或楼层内的重要区域，边表示能够连接两个区域的设施。每条边保存：

- 连接器类型；
- 可连接的楼层；
- 是否支持双向通行；
- 机器人能力要求；
- 预计通行时间；
- 风险等级；
- 当前是否可用。

### 4.2 拓扑路径选择

跨楼层任务首先在拓扑图上选择连接器，再在每个楼层内部调用Nav2。选择连接器时不应只比较距离，还应考虑机器人类型和运行状态。

例如，普通轮式机器人应禁止选择楼梯；雨天或湿滑环境可以提高坡道代价；电梯离线时应选择其他路径；人工转运虽然自动化程度低，但可以作为故障恢复路径。

这种思路使跨楼层规划成为带约束的图搜索问题，而不是简单的二维最短路问题。

## 5. 通用跨层连接器设计

### 5.1 统一抽象

系统不应把上层管理器写成专门的“电梯管理器”，而应定义通用的楼层连接器接口。每种连接器实现相同的基本生命周期：

```text
检查可用性
→ 准备进入
→ 执行跨层
→ 确认到达
→ 允许退出
```

上层任务管理器只关心连接器是否准备好、是否正在执行以及是否已经到达，不直接依赖HTTP、PLC、步态控制或人工确认等底层细节。

### 5.2 电梯与升降平台

电梯和升降平台属于“机器人本体基本静止、外部设施改变高度”的连接器。主要任务是呼叫设备、等待门或护栏打开、进入、固定位置、选择目标层、等待到达并退出。

设备运行期间应暂停正常导航和地图匹配，防止轿厢点云及垂直加速度引起错误定位。到达后通过设备状态、楼层标志或环境匹配确认目标层。

### 5.3 楼梯

楼梯属于机器人主动改变高度的高风险连接器。普通轮式底盘通常不具备安全上下楼能力，不能仅通过软件开放该功能。履带式或足式机器人需要独立的楼梯感知、姿态稳定、落脚点或接触规划模块。

在这种方案中，Nav2只负责到达楼梯入口和离开楼梯后的导航。楼梯段由专用控制器接管，完成入口对准、台阶识别、爬升或下降、平台检测和姿态恢复。

### 5.4 坡道

坡道可以部分复用连续运动控制，但仍需考虑坡度、制动、侧翻风险和地图重叠。对于缓坡，可在独立的坡道地图或局部地图中低速导航；对于长坡或与上下楼层XY投影重叠的坡道，建议将其作为单独拓扑区域处理。

坡道入口和出口应设置明确的模式切换点。进入坡道后调整速度、障碍物高度阈值和姿态限制，到达平台后再切回普通楼层导航参数。

### 5.5 人工转运

人工搬运是一种有效的工程过渡方案，也可以作为自动连接器失败后的恢复手段。机器人到达交接点后停止导航并锁定运动输出，由人员搬到目标楼层。系统收到确认后加载目标地图并执行全局重定位。

搬运过程中FAST-LIO可能产生明显漂移，因此不能沿用搬运前的地图位姿。恢复导航前必须重新建立可靠的 `map → odom` 关系。

## 6. 跨楼层任务状态机

### 6.1 推荐状态

通用状态机可以设计为：

```text
IDLE
→ PLANNING_TOPOLOGY
→ NAVIGATING_TO_CONNECTOR
→ ALIGNING
→ WAITING_CONNECTOR_READY
→ TRAVERSING_CONNECTOR
→ VERIFYING_FLOOR
→ SWITCHING_MAP
→ RELOCALIZING
→ EXITING_CONNECTOR
→ NAVIGATING_TO_GOAL
→ SUCCEEDED
```

同时设置：

```text
PAUSED / CANCELED / RECOVERY / FAILED / EMERGENCY_STOP
```

状态机的价值不只是串联步骤，更重要的是阻止系统在条件不满足时提前行动。例如，目标楼层尚未确认、地图尚未加载或定位质量不足时，Nav2必须保持未激活状态。

### 6.2 状态转换原则

每次转换至少依赖两类信息：动作结果和环境确认。导航Action返回成功只能说明机器人到达了设定坐标，不能单独证明它已经完全进入平台、已经离开楼梯或已经位于目标楼层。

重要阶段应采用多源确认，例如：

- 位置误差满足要求；
- 设备状态符合预期；
- 门或通道处于安全状态；
- 激光或视觉确认机器人完全进入或退出；
- 目标楼层标记识别成功；
- 定位匹配得分达到阈值。

## 7. 地图切换与重新定位

### 7.1 地图切换原则

当前项目通过 `database_path` 在RTAB-Map启动时指定地图数据库。工程上最稳妥的切换方式是保留Livox和FAST-LIO连续运行，只停止楼层相关的RTAB-Map定位与Nav2导航，然后使用目标楼层数据库重新启动定位模块。

推荐把系统进一步拆成：

```text
传感器与连续里程计层：Livox、FAST-LIO、静态TF
楼层定位层：RTAB-Map、全局定位服务
导航执行层：Nav2、碰撞监控
任务调度层：跨楼层管理器、连接器适配器
```

切换楼层时只重启楼层定位层，避免反复重启雷达和FAST-LIO，减少传感器初始化时间和系统波动。

### 7.2 两阶段定位

在电梯轿厢、楼梯口或狭窄平台中，当前扫描可能缺乏足够的楼层环境特征。建议采用两阶段定位：

1. 根据连接器出口的标定位姿给出粗略初始位置；
2. 机器人安全离开连接区域后，使用现有FPFH与RANSAC点云全局配准进行精定位。

精定位完成后，应检查地图匹配质量、TF连续性、机器人位姿合理性以及局部环境是否与地图一致。确认无误后清空Nav2全局和局部代价地图，再恢复导航。

### 7.3 楼层确认

地图匹配结果不能作为唯一楼层来源，因为结构相似的楼层可能产生错误匹配。建议按以下优先级融合楼层信息：

1. 楼层设施或建筑系统返回的楼层状态；
2. AprilTag、二维码或楼层标牌识别；
3. 当前地图点云匹配结果；
4. 气压计和IMU高度变化趋势。

只有多项信息一致，或可信度最高的信息明确有效时，系统才更新当前楼层。

## 8. 安全与故障处理

### 8.1 基本安全原则

跨层区域通常比普通走廊风险更高，应遵守以下原则：

- 定位无效时禁止恢复自动导航；
- 连接器状态未知时禁止进入；
- 机器人未完全进入或退出时禁止设施动作；
- 跨层阶段限制最大速度和转向速度；
- 碰撞检测和急停链路应独立于任务管理器持续工作；
- 楼梯和坡道必须校验机器人机械能力与姿态限制；
- 所有关键动作都应具有超时、取消和人工接管能力。

### 8.2 典型故障

系统至少需要处理：

- 到达连接器入口失败；
- 连接器不可用或长时间无响应；
- 进出连接区域被障碍物阻挡；
- 目标楼层确认失败；
- 目标地图加载失败；
- 全局重定位失败或匹配到错误位置；
- Nav2恢复后路径规划失败；
- 通信中断、急停或底盘故障。

恢复策略应优先保证机器人停止在安全位置。可以依次尝试重新感知、重新定位、返回入口、切换备用连接器或请求人工接管，而不应无限重复同一动作。

## 9. 与现有项目的结合

现有项目无需替换FAST-LIO、RTAB-Map或Nav2。主要新增能力包括：

- 楼层与连接器配置；
- 建筑拓扑图；
- 跨楼层任务管理器；
- 通用连接器接口及不同类型的适配器；
- 地图切换管理；
- 重定位质量判断；
- 跨层状态、进度和异常反馈。

现有的Nav2目标发送能力可用于楼层内分段导航；现有全局定位模块可用于目标楼层精定位；现有生命周期控制方式可用于地图切换期间关闭和恢复Nav2。项目改造重点应放在这些已有能力之上的任务编排，而不是重新实现底层导航算法。

## 10. 分阶段实施路线

### 第一阶段：多楼层地图基础

分别完成各楼层建图、点云导出和单层导航测试。验证机器人使用任意楼层数据库都能启动、定位和导航。

### 第二阶段：手动跨层闭环

先采用人工搬运方式验证完整流程：到达交接点、暂停导航、人工移动、切换地图、重新定位和继续导航。该阶段能够低风险验证任务管理、地图切换和状态机。

### 第三阶段：连接器仿真

使用模拟接口代替真实设施，验证等待、超时、取消、失败恢复和备用路径选择。此时重点是软件流程的确定性，而不是设备控制。

### 第四阶段：接入真实跨层设施

根据实际机器人和建筑条件接入电梯、坡道、楼梯控制器或升降平台。逐步完成入口对准、进出检测、楼层确认和安全联锁。

### 第五阶段：系统化验证

进行重复性、异常和安全测试，包括不同起终点、连接器被占用、定位失败、门未打开、坡道有障碍、网络中断和人工急停等情况。

## 11. 结论

对于当前 `xz` 项目，跨楼层导航最合理的技术路线是“多楼层独立地图、建筑拓扑规划、楼层内Nav2导航、楼层间专用控制、目标楼层重新定位”。这种方案符合现有系统的二维导航基础，能够最大程度复用FAST-LIO、RTAB-Map、Nav2和全局定位模块。

系统的核心不是某一种电梯或楼梯控制方法，而是建立统一的跨层任务框架。通过连接器抽象，上层可以用同一种方式调度电梯、楼梯、坡道、升降平台和人工转运；通过状态机和安全门控，可以确保地图、楼层和定位关系未确认时机器人不会误动作。

建议首先以人工转运完成多楼层软件闭环，再逐步接入真实跨层设施。这样能够把地图切换、重新定位和任务调度等共性问题与具体设备控制问题分开验证，降低整体实施风险。
