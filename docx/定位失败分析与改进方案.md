# 定位失败分析与改进方案

**作者**: ZiyangWang  
**日期**: 2026-06-27

---

## 1. 问题背景

本项目使用 RTAB-Map 替代 AMCL 进行定位，全局重定位通过 HDL Global Localization (FPFH+RANSAC) 完成。当前已实现内点率（inlier_fraction）过滤机制，但仍存在以下问题：

- 全局重定位仅依赖单一指标（inlier_fraction），缺乏多维度判断
- 导航过程中持续定位无监控机制，定位丢失后无法自动检测
- 协方差为写死值，不反映实际匹配置信度

本文档对定位失败的场景进行系统分析，并提出可行的改进方案。

---

## 2. 定位失败场景分类

### 2.1 全局重定位阶段（开局一次性）

| 场景 | 原因 | 当前处理 |
|------|------|----------|
| 无候选返回 | 地图与当前场景差异大，RANSAC 无法找到满足 inlier > 0.35 的解 | 重试 3 次后 exit 0，提示手动定位 |
| inlier 偏低 | 匹配有部分重合但不充分（0.35 < inlier < 0.98） | 当前阈值 0.98 会拒绝，重试后提示手动定位 |
| 错误匹配 | 对称场景（长走廊、重复结构）导致 RANSAC 匹配到错误位置 | inlier 可能很高，当前机制无法识别 |
| 扫描超时 | FAST-LIO 未启动或激光话题名不匹配 | exit 1，启动脚本报错 |
| 地图质量差 | PCD 地图稀疏、特征不足、高度滤波过度 | FPFH 特征提取效果差，匹配困难 |

### 2.2 导航持续定位阶段

| 场景 | 原因 | 当前处理 |
|------|------|----------|
| 定位漂移 | 长时间无 loop closure，里程计误差累积 | 无检测，map→odom TF 静默漂移 |
| 错误 loop closure | 相似场景导致 RTAB-Map 匹配到错误关键帧 | 位姿跳变，无告警 |
| 定位丢失 | 环境变化（新障碍物、布局改变）导致无法匹配 | covariance 持续增大，但无人监控 |
| 绑架问题 | 机器人被搬移，RTAB-Map 不知道 | 继续用旧位姿，严重偏差 |
| 动态障碍物 | 大量移动物体干扰匹配 | 可能导致匹配不稳定 |

## 3. 现有机制分析

### 3.1 全局重定位的置信度指标

**FPFH+RANSAC 返回的指标：**

- `inlier_fraction` — 内点比例，当前唯一的过滤标准
- `matching_error` — 平均匹配距离，计算了但未参与过滤

**不足：**
- 单一阈值无法区分"正确匹配"和"恰好部分重合的错误匹配"
- 没有考虑匹配的空间分布（内点可能集中在一个小区域）
- 没有多候选交叉验证

### 3.2 RTAB-Map 持续定位的置信度指标

RTAB-Map 每帧发布的数据：

| 指标 | 来源 | 含义 |
|------|------|------|
| `localizationCovariance` | 图优化结果 | 6×6 协方差矩阵，反映定位不确定性 |
| `loopClosureId` | 匹配结果 | > 0 表示成功匹配到关键帧 |
| `LoopVisual_inliers_ratio` | 视觉匹配 | 视觉内点比例 |
| `LoopLinear_variance` | 匹配质量 | 线性匹配方差 |
| `LoopAngular_variance` | 匹配质量 | 角度匹配方差 |
| `LoopOptimization_error` | 图优化 | 优化后的残差 |

**不足：**
- `loc_thr` 未配置，诊断功能未启用
- 无节点订阅 `/statistics` 做实时判断
- covariance 虽有值但无人使用

## 4. 改进方案

### 4.1 全局重定位改进

#### 方案 A：增加 matching_error 阈值（低成本）

**思路**：在现有 inlier_fraction 基础上，增加 matching_error 上限检查。

**实现**：
```python
# global_localization_node.py
MAX_MATCHING_ERROR = 0.5  # 平均匹配距离上限（米）

if inlier < min_inlier or error > MAX_MATCHING_ERROR:
    reject and retry
```

**优点**：改动极小，只加一行判断  
**缺点**：两个独立阈值仍无法全面评估，需要调参

#### 方案 B：多候选交叉验证（中成本）

**思路**：请求多个候选（max_num_candidates > 1），比较 top-1 和 top-2 的 inlier 差距。差距大说明 top-1 明显更优，结果可信。

**实现**：
```python
req.max_num_candidates = 5
# ...
if len(res.poses) >= 2:
    gap = res.inlier_fractions[0] - res.inlier_fractions[1]
    if gap < 0.1:  # top-1 和 top-2 差距太小，说明有歧义
        reject and retry
```

**优点**：能识别对称场景的歧义匹配  
**缺点**：RANSAC 计算量增加，响应时间变长

#### 方案 C：动态协方差（低成本）

**思路**：根据实际 inlier_fraction 动态调整发布的协方差，而不是写死 0.25。

**实现**：
```python
# inlier 越高 → 协方差越小 → RTAB-Map 越信任这个位姿
cov_xy = max(0.01, 1.0 - inlier)  # inlier=1.0 → cov=0.01, inlier=0.5 → cov=0.5
cov_yaw = cov_xy * 0.272  # 保持 yaw/xy 比例

_COVARIANCE[0]  = cov_xy
_COVARIANCE[7]  = cov_xy
_COVARIANCE[35] = cov_yaw
```

**优点**：RTAB-Map 能根据协方差决定是否信任初始位姿  
**缺点**：需要实验确定 cov 和 inlier 的映射关系

#### 方案 D：二次验证（中成本）

**思路**：全局重定位得到位姿后，用 RTAB-Map 做一次局部匹配验证。如果 RTAB-Map 能在该位姿附近找到匹配，说明位姿可信。

**实现**：
1. 发布 `/initialpose`
2. 等待 RTAB-Map 处理若干帧
3. 检查 `localizationCovariance` 是否收敛（值变小）
4. 如果 covariance 持续为 9999，说明 RTAB-Map 无法在该位姿定位，撤销初始位姿

**优点**：利用 RTAB-Map 自身能力验证，最可靠  
**缺点**：流程复杂，需要额外等待时间

---

### 4.2 导航持续定位改进

#### 方案 E：启用 loc_thr 诊断（低成本，推荐）

**思路**：配置 RTAB-Map 的 `loc_thr` 参数，启用内置诊断。

**实现**：
```yaml
# 在 RTAB-Map 参数中添加
loc_thr: 2.0  # 定位误差超过 2m 则报错
```

**效果**：
```bash
ros2 topic echo /diagnostics
# "Localized." — OK
# "Localization error is high!" — 定位漂移
# "Not localized!" — 未定位
```

**优点**：零代码改动，RTAB-Map 原生支持  
**缺点**：只有诊断信息，没有自动响应

#### 方案 F：定位监控节点（中成本，推荐）

**思路**：编写独立节点，订阅 `/diagnostics` 或 `/rtabmap/localization_pose`，实时监控定位状态，超阈值时触发响应。

**建议功能**：
```
监控循环（每 1 秒）:
  读取 localizationCovariance
  ├── cov[0] >= 9999  → "Not localized"，暂停导航，发布警告
  ├── cov[0] > 阈值    → "Drifting"，降低速度，增加扫描频率
  └── cov[0] <= 阈值    → "OK"，正常运行
```

**响应策略**：
- 轻度漂移：记录日志，继续导航
- 中度漂移：暂停当前任务，原地旋转重新定位
- 严重丢失：停止导航，请求人工介入

**优点**：可定制响应策略，可集成到 Nav2 行为树  
**缺点**：需要开发和调试

#### 方案 G：定位丢失自动恢复（高成本）

**思路**：定位丢失时自动触发重定位（类似开局的全局重定位）。

**实现**：
1. 监控节点检测到定位丢失
2. 加载地图 PCD，调用 HDL `/query` 服务
3. 如果得到可靠结果，发布 `/initialpose`
4. RTAB-Map 重置位姿

**优点**：全自动，无需人工干预  
**缺点**：流程复杂，可能在错误位置反复重定位；需要地图 PCD 常驻内存

## 5. 方案优先级与推荐

| 优先级 | 方案 | 成本 | 效果 | 推荐理由 |
|--------|------|------|------|----------|
| P0 | E: 启用 loc_thr | 极低 | 中 | 一行配置即可启用持续定位监控 |
| P0 | C: 动态协方差 | 低 | 中 | 让 RTAB-Map 知道初始位姿的可信度 |
| P1 | A: 增加 error 阈值 | 低 | 中 | 补充 inlier 不足的场景 |
| P1 | F: 定位监控节点 | 中 | 高 | 实时检测 + 自动响应 |
| P2 | B: 多候选交叉验证 | 中 | 中 | 解决对称场景歧义 |
| P2 | D: 二次验证 | 中 | 高 | 最可靠的验证方式 |
| P3 | G: 自动重定位恢复 | 高 | 高 | 全自动但风险较大 |

## 6. 近期建议实施步骤

### 第一步：低成本快速见效（1-2 天）

1. 启用 `loc_thr`：在 RTAB-Map 参数中添加 `loc_thr:=2.0`
2. 实现动态协方差：修改 `global_localization_node.py`，根据 inlier 计算协方差
3. 增加 matching_error 阈值：在 Python 客户端加 error 上限检查

### 第二步：监控体系建设（3-5 天）

1. 编写定位监控节点，订阅 `/diagnostics`
2. 实现日志记录（定位状态随时间变化）
3. 在 RViz 中添加定位状态显示

### 第三步：自动恢复机制（1-2 周）

1. 评估自动重定位的可行性
2. 实现定位丢失检测 → 自动重定位流程
3. 与 Nav2 行为树集成，实现导航任务级别的容错

## 7. 测试验证方案

### 7.1 全局重定位测试

- **正常场景**：在建图原点启动，验证 inlier 和 error 值
- **偏移场景**：在距原点 5m/10m/20m 处启动，观察匹配质量变化
- **旋转场景**：机器人朝不同方向启动，验证旋转不变性
- **失败场景**：在未建图区域启动，验证失败路径是否正确

### 7.2 持续定位测试

- **正常导航**：从 A 点到 B 点，监控 covariance 变化
- **长距离**：跨越整个地图，观察漂移累积
- **遮挡测试**：经过临时障碍物（如行人），观察定位恢复能力
- **绑架测试**：手动搬移机器人，观察检测和恢复时间

---

## 8. 总结

当前全局重定位仅依赖 inlier_fraction 单一指标，持续定位无监控。短期内通过启用 `loc_thr` 和动态协方差可以低成本改善；中期通过定位监控节点实现实时检测；长期可考虑自动重定位恢复。建议按优先级分步实施，每步都进行充分测试验证。
