## 1. 报告结论

本次问题不是单一参数导致，而是以下四类问题叠加形成的：

1. **FAST-LIO 在室外空旷、地面占主导的环境中可观测性不足**。第二次导航目标触发了约 `-1.0 rad/s` 的长时间原地旋转，缺少平移视差，数秒后 FAST-LIO 开始快速发散。
2. **系统存在明显计算和消息队列积压**。FAST-LIO 的点云和里程计输出只有约 `6 Hz`，低于雷达配置的 `10 Hz`；全话题 rosbag 录制约 `30 MB/s`，进一步放大了 CPU、内存、磁盘和 DDS 压力。
3. **地图编辑后的地图存在确定性错误：未知区域被全部转换成了自由区域**。这会使全局规划器把室外未探索区域当作可通行区域，从而产生错误路径和不合理旋转。

因此，本次故障的主要因果链为：

```text
编辑地图未知区被误转为自由区
        +
RViz、RTAB-Map、相机、Nav2、全话题 rosbag 同时运行
        ↓
规划进入未观测区域 / 出现长时间高速旋转 / 系统消息积压
        ↓
室外平面退化 + 缺少平移视差 + FAST-LIO 在线外参估计
        ↓
FAST-LIO 状态发散
        ↓
错误的 odom、点云和 TF 继续进入 RTAB-Map、Nav2、costmap
        ↓
定位漂移、路径异常、点云过期、防撞数据被丢弃
```

### 2.3 室外点云几何特征

对 `/cloud_registered_body` 的抽样统计显示：

- 点云中位距离约 `5 m`；

### 2.4 点云和里程计延迟

以 rosbag 接收时间减去消息 `header.stamp` 统计：

| 话题 | 中位延迟 | 90% 分位 | 最大值 |
|---|---:|---:|---:|
| `/livox/imu` | 约 1.28 s | 约 1.30 s | 约 1.68 s |
| `/cloud_registered_body` | 约 4.70 s | 约 5.46 s | 约 7.59 s |
| `/Odometry` | 约 5.40 s | 约 7.37 s | 约 9.95 s |

这里必须区分两种延迟：

1. `/livox/imu` 稳定存在约 `1.27 s` 的偏移，更像是**传感器时钟与主机系统时钟的固定基准差**。
2. FAST-LIO 输出比 IMU 又多出约 `3～8 s`，这是**处理速度不足、消息排队或录包造成的动态积压**。

因此：

> 不应直接把 `time_offset_lidar_to_imu` 设置成 `1.27`。

该参数表示 LiDAR 与 IMU 两种传感器之间的相对时间偏移，不是传感器时钟与电脑系统时钟的偏移。错误设置反而会破坏点云去畸变。

## 3. 问题一：为什么室内里程计稳定，室外空旷会发散

### 3.1 核心原因：室外几何退化

FAST-LIO 需要利用点到局部平面的残差约束位姿。室内通常有：

- 墙面；
- 门框；
- 柱子；
- 墙角；
- 天花板；
- 家具和其他立体结构。

这些不同方向的平面和边缘能够同时约束多个自由度。

室外空旷区域通常只有大面积地面，远处物体较少或距离过远，点云呈现单一平面结构。单纯依赖地面时：

- 高度、横滚和俯仰相对容易被约束；
- 平面内的前后、左右和平面旋转约束明显变弱；
- IMU 偏置或点云匹配的小误差容易逐步累积。

### 3.2 长时间原地旋转加重退化

本次数据中，第二个导航目标触发了约 20 秒的高角速度旋转。原地旋转存在两个问题：

1. 缺少平移运动，不能产生有效平移视差；
2. 室外地面点旋转后的几何形态相似，匹配容易出现错误方向或错误位移。

因此，长时间原地旋转是本次 FAST-LIO 发散的重要触发条件。

### 3.3 在线外参估计增加不稳定因素

当前配置为：

```yaml
mapping:
  extrinsic_est_en: true
```

导航运行阶段，如果雷达和 IMU 已经完成机械固定及离线标定，继续在线估计外参会增加状态维度。在几何退化、纯旋转、振动或时序积压时，外参和运动状态可能相互补偿，把匹配误差吸收到错误的外参或姿态中。

建议导航阶段固定外参：

```yaml
mapping:
  extrinsic_est_en: false
```

### 3.4 负载和延迟进一步破坏去畸变与闭环处理

点云积压本身不一定直接改变消息中的传感器时间，但会造成：

- FAST-LIO 无法实时处理；
- 输入队列持续增长；
- Nav2 使用数秒前的位姿和点云；
- 控制指令根据过期状态继续旋转；
- 定位错误无法及时触发停车。

所以本次室外发散不是单纯的 FAST-LIO 算法问题，而是“环境退化 + 运动方式不利 + 系统过载 + 在线外参估计”共同作用。

## 4. 问题二：点云和里程计延迟是什么原因

### 4.1 延迟链路

```text
MID360 数据到达
   ↓
Livox driver 发布原始雷达和 IMU
   ↓
FAST-LIO 缓存、同步、去畸变、匹配、更新局部地图
   ↓
发布 /cloud_registered_body 和 /Odometry
   ↓
DDS 分发给 RTAB-Map、RViz、STVL、collision_monitor 等多个节点
```

任一阶段处理速度低于输入速度，就会形成队列积压。

### 4.2 本次主要负载来源

本次同时运行了：

- Livox driver；
- FAST-LIO；
- Orbbec 彩色和深度相机；
- `rgbd_sync`；
- RTAB-Map；
- RViz；
- Nav2 local/global costmap；
- STVL；
- collision monitor；
- ForbiddenAreaLayer；
- CUDA MPPI；
- 全话题 rosbag 录制。

其中点云、彩色图、深度图、costmap 和 TF 都是高频或大消息。全话题录制会增加序列化、DDS 拷贝、磁盘写入和缓存压力。

### 4.3 延迟的直接后果

1. collision monitor 认为点云过旧，直接忽略点云；
2. STVL/local costmap 使用过期障碍位置；
3. 控制器基于旧位姿继续输出速度；
4. RViz 显示的点云落后于机器人实际位置；
5. 定位已经异常时，导航系统不能及时停止。

## 5. 问题三：为什么加入地图编辑和禁行区后才出现

### 5.1 确定性错误：未知栅格被转换成自由栅格

编辑地图文件：

```text
pgm_map/map.yaml
pgm_map/map.pgm
```

PGM 像素统计：

| 像素值 | 含义 | 数量 |
|---:|---|---:|
| 205 | 未知区域 | 132,792 |
| 254 | 自由区域 | 90,865 |
| 0 | 障碍区域 | 1,937 |

但是 rosbag 中实际发布的 `/map` 为：

| 栅格值 | 数量 |
|---|---:|
| 未知 `-1` | 0 |
| 自由 `0` | 223,657 |
| 障碍 `100` | 1,937 |

并且：

```text
132792 + 90865 = 223657
```

即原地图中的全部未知区域都被当成了自由区域。

RTAB-Map 原始地图 `/rtabmap/map_raw` 仍保留约 `132277` 个未知栅格，说明未知区域消失发生在编辑地图加载/发布链路，而不是 RTAB-Map 原始建图阶段。

### 5.2 代码原因

当前 `storage.py` 使用：

```python
occupied_limit = int(round((1.0 - occupied_thresh) * 255.0))
free_limit = int(round((1.0 - free_thresh) * 255.0))

grid[image <= occupied_limit] = 100
grid[image >= free_limit] = 0
```

而 `map.yaml` 使用：

```yaml
occupied_thresh: 0.65
free_thresh: 0.25
```

像素 `205` 对应的占用概率约为：

```text
(255 - 205) / 255 ≈ 0.196
```

由于 `0.196 < 0.25`，未知像素被判定为自由。

建议改成基于占用概率的严格比较：

```python
occupancy = (255.0 - image.astype(float)) / 255.0
grid = np.full(image.shape, -1, dtype=np.int16)
grid[occupancy > occupied_thresh] = 100
grid[occupancy < free_thresh] = 0
```

并统一使用：

```yaml
occupied_thresh: 0.65
free_thresh: 0.196
```

需要同时修改：

- 已存在的 `pgm_map/map.yaml`；
- `src/map_paint_editor_plugin/scripts/map_editor/storage.py` 的加载逻辑；
- `storage.py` 保存 YAML 时写入的默认阈值。

只修改 YAML 而不修正当前的取整和 `>=` 比较逻辑，仍可能在边界值上把 `205` 错判为自由。

### 5.3 该错误如何影响导航

未知区域变成自由区域后：

- 全局规划器会认为室外未探索区域可通行；
- 路径可能穿过地图外、无点云约束区域或真实障碍；
- 控制器为了追踪错误路径可能长时间旋转；
- 机器人被引导进入 FAST-LIO 最容易退化的空旷区域。

该地图错误**不直接修改 FAST-LIO 的滤波状态**，但会通过错误规划和运动方式间接触发 FAST-LIO 发散。

### 5.4 本次禁行区多边形实际上没有生效

数据包中：

```text
/forbidden_areas_markers
```

共 131 条消息，但全部是空 `MarkerArray`，没有实际禁行区多边形。

启动日志中运行了：

```text
forbidden_area_visualizer.py
```

但没有启动：

```text
map_paint_editor.py
```

因此，本次故障不能归因于“禁行区多边形画错了”。更准确的结论是：

> 加入该功能时同时切换了整套地图与导航配置，真正生效的是编辑地图、ForbiddenAreaLayer 插件以及新的控制器和参数，而不是某个实际禁行多边形。

## 6. 整改方案

### 6.1 保证安全

1. 增加定位健康监控，出现以下任一情况立即发布零速度并取消导航：
   - `abs(z) > 0.3 m`；
   - `abs(roll)` 或 `abs(pitch) > 10°`；
   - odometry 瞬时位移或速度超过底盘物理上限；
   - `/Odometry` 或点云超过允许时间未更新；
2. FAST-LIO 发散后必须重启定位链路，不能只重新发送目标点。

### 6.2 修复地图语义

1. 修复 `storage.py` 的占用概率转换；
2. 将地图 YAML 的 `free_thresh` 统一为 `0.196`；
3. 重新加载地图并验证：

```bash
ros2 topic echo /map --once
```

必须确认 `/map.data` 中仍存在大量 `-1` 未知栅格。

验收目标：

```text
未知栅格数量应接近 PGM 中像素 205 的数量，而不是 0。
```

### 6.3 降低 FAST-LIO 和系统负载（性能有影响）

初始建议：

```yaml
point_filter_num: 3
filter_size_surf: 0.25
filter_size_map: 0.25
cube_side_length: 200.0
blind: 0.5
extrinsic_est_en: false
path_en: false
```

同时：

- 暂时关闭 `rtabmap_viz`；
- RViz 只显示必要话题；
- 不显示累计大点云；
- 禁用非必要相机流；
- 检查是否可以启用进程内通信或减少同一大点云的订阅者；

### 6.4 优化地图编辑和禁行区

1. `updateCosts()` 在禁行区为空时直接返回；
2. 缓存禁行区栅格掩膜或栅格包围盒；
3. 地图编辑器不要在导航中持续运行；
4. 绘制过程中不要每约 `150 ms` 发布整张 `/map`；
4. 解决两个/map发布的问题
5. 不要在每次地图发布后自动清空全局 costmap；
6. 默认关闭自动重发最近导航目标；
7. 地图编辑完成后保存、退出编辑器，再重新启动导航。

## 7. 总结

1. **室内不发散、室外空旷发散**：主要是室外点云平面退化，长时间原地高速旋转缺少平移视差，再叠加在线外参估计和系统积压，最终导致 FAST-LIO 滤波器发散。
2. **点云和里程计延迟**：约 `1.27 s` 是较稳定的传感器时钟与主机时钟偏移；其余约 `3～8 s` 是 FAST-LIO、DDS、可视化、相机、Nav2 和全话题录包共同造成的处理队列积压。
3. **FAST-LIO 参数问题**：当前点云保留过密、地图范围过大、盲区偏小、在线外参估计开启，不适合当前已经过载且存在室外退化的导航场景。IMU 噪声参数需标定后再调整。
4. **加入地图编辑和禁行区后出现问题**：最关键的新问题是编辑地图把全部未知区域转换成了自由区域；同时配置还更换成 CUDA MPPI 并增加了插件和计算负载。此次禁行区 Marker 实际为空，因此不能把问题简单归咎于禁行多边形本身。
